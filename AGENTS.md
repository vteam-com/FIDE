# Rules

- no magic numbers
- document all public classes, methods, functions
- fcheck --strict must score 100%
- always apply DRY: before writing new code, look for an existing widget, helper or constant to reuse; extract shared code instead of copying it
  - DRY covers widget configuration too: the same Flutter widget (`TabBar`, bordered `Container`, `TabBarView`, …) set up the same way in more than one file belongs in one shared widget under `lib/widgets/`
  - when reviewing for DRY, compare across files and folders, not just within one file or diff: list every place a widget is built and compare the calls
  - UI elements that should look alike but render differently are a sign of duplicated code that has drifted
  - DRY aims at consistent code and consistent rendering: when UI code is almost the same and differs only by a few attributes (color, radius, padding, icon size, divider color, …), remove the differences rather than adding parameters to keep them
  - keep the base building blocks simple and few; avoid snowflake UI elements and one-off variants
  - the same content on two surfaces (a center page and a side panel) is one widget that fits its width, not two renderings: the project's identity is `ProjectHeader`, its quality `ProjectQualityCard`, in the overview and the Info tab alike
  - DRY covers features too: list every user-facing action (button, menu item, command) across all panels and compare what each one does, not only its code; two actions doing the same job under different names, widgets or services are duplicates — keep one
- one visible progress indicator per task: a panel with a `RefreshButton` shows its work as the ring around that button, whoever started it; other panel work shows as a `BusyBar` (thin horizontal bar atop its content, `LoadingIndicator` while nothing is shown yet); a spinner only on the button that started the task, the others just disabled; besides that, every side panel tab whose work outlasts its panel rings its tab icon while that work runs (`PanelTabSpec.busy`), so it shows from the other tabs: AI (chat replies and tasks, Ollama setup), Preview, Analyzer, Info, Run, Test
  - the tab ring wins: it shows whether its tab is selected or not, so work a tab rings for draws nothing else that spins in its panel: no `BusyBar`, no `LoadingIndicator` bar (a loading message shows alone, as `EmptyState`), no spinner, and the panel's `RefreshButton` is only disabled meanwhile, without its ring
  - the ring must never start the work it shows, nor a tab's badge the work it counts: read a source that works once created (an analysis, a scan) through `follow` / `followBusy`
  - work kept in a widget's own state or an autoDispose provider ends with its panel, so it can't ring its tab; move it into a kept provider first
  - a task changing the project's files at a click (a quick fix without the AI, Split from the Organized view, the Analyzer tab's Move and Fix) blocks the app with `BlockingTaskDialog.run`, so nothing edits the files meanwhile: a scrim, the task's title, the step it is at (`BlockingTask.report`) under a `BusyBar`, and Cancel, which the task checks between steps and before writing what a step planned, so no step is left half done; it is that task's one indicator, the button starting it only disabled; AI tasks keep running in the AI panel, with its Stop
- the shared UI blocks: `PanelHeader` atop a side panel, `RefreshButton` to run a check again (end of the header), `OutlinedSurface` for any box, `SectionTitle` style for section headings, `LocationRow` for a place in the code, `TreeBranch` for tree levels, `ChoiceButtons` for one-of-N picks, `BulletList` for bulleted lines, `OutputPanel` for any console output (its header always offers Copy, Wrap and Clear; Clear drops the text at its source, so the console hides until there is output again), `TaskButton` for any task one click starts (Build, Run, Test, AI Send, AI commit message, `RefreshButton`): while it runs a ring spins around it and a red Stop replaces it when the task can be stopped, its disabled icon when not — never a bare spinner or a Stop without the ring; `TaskRing` is that ring, shared with the busy tab icons; `BlockingTaskDialog` for a task changing the project's files
- every text style lives in `AppTextStyle` (`lib/constants/constants.app_text_style.dart`), built on the `AppFontSize` scale; never write `TextStyle(...)`, `textTheme.*`, `fontSize:`, `fontWeight:` or line heights elsewhere — pick a style there and only add a state color with `copyWith(color: …)`; a missing style is added to that file
- every color must read at WCAG 2 AA in both themes: text 4.5:1 (`AppTheme.minTextContrast`), icons 3:1 (`AppTheme.minGlyphContrast`); `test/color_contrast_test.dart` checks it, so add each new pairing there
  - text and glyphs on a fill (badge, message, filled button) take `AppTheme.onFill(fill)`; status colors drawn straight on a surface take `readableIn` / `AppTheme.readable`
  - dim text with `onSurfaceVariant`, never with alpha on `onSurface` or a status color: translucent text falls below AA
- never use the floppy disk icon (`Icons.save*`) for Save, Commit, Apply or Persist actions: use `Icons.download`, as the editor's Save does (Apple's `square.and.arrow.down`), or a plain text label as Apple's UX does
- a button's label is a short action name: a verb, with its object when needed, in Title Case (`Generate Previews`, `Stage All`, `Translate`), never a sentence or a phrase saying what it applies to, how many or how (`Write previews of PracticeScreen with AI`, `Generate Previews for 3 more widgets`, `Translate to German`); that goes in the message above it, the row it sits in, or its tooltip
- `fcheck --fix` can reformat unrelated files; revert changes it makes outside the task
- fCheck (package `fcheck`, repo `../fcheck`) is the brain for analyzing Flutter/Dart projects; FIDE consumes its public API (`package:fcheck/fcheck.dart`) and never reimplements analysis
  - never change fCheck's source (code, tests, docs) without the user's authorization: the user reviews every fCheck change
  - when FIDE needs a new finding or metric, propose the fCheck change to the user first (it has its own users, so keep it general); only after they authorize it, add it to fCheck and use it from FIDE
  - never import `package:fcheck/src/...`; export what FIDE needs from fCheck instead
  - `AnalyzeFolder.analyze()` is synchronous: run it with `Isolate.run`
  - an analysis under evaluation (the Analyzer tab's File Layout and Repeated Widget Settings, the Color contrast and Widget States checks) lives in FIDE until the user decides it has proven its value, written as fCheck's analyzers are (plain Dart without Flutter, parsed code, `// ignore: fcheck_<name>` comments) so it moves into fCheck as is
  - refactoring suggestions for widgets tell views from widgets, one way: File Layout's (`FileLayoutAnalyzer.viewsOf`: a file declaring a screen, or named as a view in a views folder), never by folder; Repeated Widget Settings shows each place in a view or a widget
- AI panel: when the user asks to fix or change code, the AI edits the project files (through `CodeEditAgent`); it never replies with code for the user to paste
  - code decides whether a prompt asks for a change (`PromptIntent`), not the model: any other prompt is answered by an agent whose tools only read, as a local model given editing tools edits files even for "2+2="
  - the agent is offered FIDE's whole-project quick fixes only when the request names their subject (`QuickFix.topics`), never all of them
  - the agent runs the commands a change needs itself (`run_command`), never asking the user to; only the allowlisted `ProjectCommand`s (pub dependency chores, `flutter gen-l10n`, `dart fix`/`format`, `dart run build_runner build`, `pod install`/`update`), run without a shell, one per call, with arguments inside the project; never a shell, `rm` or any other executable: a local model tries `rm pubspec.lock && …`, and runs a script it just wrote when it can; only editing tasks get it, never a question
- a stateful widget is two classes in one file: the widget and its `State`, private (`_FooState`), which is part of the widget, never a class of its own; every part of FIDE treats them so, through `WidgetStates`
  - Split Classes makes a public `State` private instead of moving it, and moves a stateful widget with its `State`; a `State` stays public, beside its widget, only when another library of the app names it (`GlobalKey<FooState>`), never for a test: a widget's `State` is private to its widget, so a test reaching into it is wrong, never made right by `@visibleForTesting`
  - the Widget States check (`WidgetStateAnalyzer`, a quality issue, so the overview, the Info panel and the light bulb show it) flags a `State` apart from its widget, in a part file or a file of its own, and a public one no other library names; a State whose line ends with `// ignore: fcheck_widget_state` is left alone by the check and Split Classes alike; Fix States moves it beside its widget and makes it private, through Split Classes' planner (`statesOnly`)
  - each test line reaching into a `State` (`tester.state<FooState>`, its widget's `createState()`, a variable holding one, even `dynamic`, a private name too) is an error of the "Tests reaching into States" issue, which Fix States fixes in the same click as the `State` (`_TestCleaner`): the methods tests call that use nothing of the `State` move out of it as top-level functions the tests call directly (`_PureMethods`), so those checks stay; every other statement reaching into it goes, with what only it used, a test, `setUp` or group left empty, and the imports no longer used; a reach outside a test, hook, group or `main` refuses the fix, saying where. No AI fix: qwen3-coder, asked twice to rewrite such tests (the second time told never to), swapped each check for a bare `findsOneWidget` in ~200 s
  - a place in a `State` is named after its widget (Repeated Widget Settings), and the One class per file, Widget States and Tests reaching into States issues teach the rule to the user
  - a file opting out with `// ignore: fcheck_one_class_per_file` (top of file, before any code) is left alone: go by fCheck's `FileMetrics.isOneClassPerFileCompliant`, which honors it, never by counting classes again
- FIDE is strictly for Flutter/Dart projects, so it knows the whole context and what is expected: a finding's fix is one click of deterministic code doing every step the fix takes, across `lib` and the tests (moving, renaming, rewriting callers and tests, removing what goes, imports included), checked to compile, never a sequence of clicks, hand edits or the AI
- prefer deterministic code refactorings (quick fixes) over sending work to the AI: the local model is too slow for mechanical changes; leave the AI only what code cannot decide or rewrite
  - a refactoring that moves or writes code across files (File Layout's Move and Move All, Split Classes, the Repeated Widget Settings fixes) never adds a Layers issue: FIDE builds the dependency graph the change would make (`ImportGraph`) and fCheck judges it with `validateLayers`, the full Layers check `fcheck` reports (file and folder cycles, wrong layers, upward folder edges); fix the issue in the same change when code can (File Layout moves along the files that prevent it, Split Classes moves a class its file would import back into a part file), else refuse it with fCheck's message
  - widget previews are generated by code alone (`PreviewGenerator`), never by the AI: each required argument gets a sample picked from its type, building the project's and its packages' own classes and importing what they need; a widget code can't build says which type, with no AI fallback
- AI is private, local and fast: it runs only on the local Ollama model, offline, and the code never leaves the computer; no cloud or remote AI provider (they were tried and removed as too complex to set up)
  - the user picks the model in the AI panel's footer among the few FIDE offers (`LocalModel`), each shown with the memory it needs: MiMo 9B by default, for 16 GB computers, at half Qwen3 Coder's memory and about as fast on the agent benchmark, a little less reliable on multi-file edits (9 of 11 features and 10 of 11 Fix Builds passed); Qwen3 Coder 30B (every one passed) and Qwen 3.8 27B (the only one answering the large-codebase question right, slower) for 32 GB; picking one not downloaded downloads it. A model joins the list only if it calls tools and passes the agent benchmark at least as MiMo does: gpt-oss:20b, fastest of all, was turned down for failing every multi-file feature and a Fix Build
- never regress the local AI's speed or judgment; every AI change keeps these, and re-measures against a real Ollama model when it touches the agent, its prompts or tools:
  - keep the model's context small, as it slows down sharply as it fills (on an M4 Max, qwen3-coder reads 1,200 tokens/s near the start, 300 at 24k; writes 129 tokens/s, 25 at 28k): the agent stays within `ChatModel.contextBudget`, dropping the oldest tool outputs first, never letting Ollama overflow and cut the conversation
  - tools return bounded output: `list_files` capped, files read in parts, `search` before reading, history capped
  - tools answer with what the model would otherwise read the file again for: an edit answers with the lines it changed, `check_build` quotes the line of code under each error, a replace it can't make shows where the text (or its first line) is; `replace_in_file` takes `replace_all` for renames; every step costs a round trip
  - the agent checks its work with `dart analyze` (seconds), building only to fix a failed build (a release build takes minutes)
  - stream replies, warm the model up when the prompt takes focus, and retry Ollama's malformed tool calls with a request that says what went wrong: the same request writes the same broken call
  - a call the model repeats with nothing changed in between gets its earlier result and a note instead of running again, and the agent stops after `AppMetric.aiMaxRepeatedCalls` of them: a local model can loop on one, such as `check_build`
  - a question stopped so, or by its step cap (`AppMetric.aiMaxAnswerRounds`), gets one last request offered no tool, answering from what the model read: MiMo, asked "find me one typo in my project", kept reading after it had read the misspelled file, ending 3 times in 5 on "ask a narrower question"; with the last request every run answers, though not always right
  - every agent tool takes at least one required parameter: qwen3-coder can leave a call with none unclosed (`<function=…>` without `</function>`), which Ollama fails as "XML syntax error … unexpected EOF"
  - the routing above: a question gets read-only tools, quick fixes only when named
  - reference timings to stay at or under: "2+2=" answered in one step without tools, in ~4 s; a question needing one file read ~5 s; a rename in one file 6 steps, ~8 s; upgrading one package through `run_command` ~10 steps, ~12 s; a multi-file Fix Build of 10 errors ~20 steps, ~40 s; the step cap (`AppMetric.aiMaxToolRounds`) stays far above what a task takes
    - re-measure them with `FIDE_AI_BENCH=3 flutter test test/ai_agent_benchmark_test.dart`, which runs the real agent on a small Flutter app (plus a question about FIDE's own code), each run checked by `dart analyze`; `FIDE_AI_BENCH_TASKS=rename,fixBuild` picks tasks, and `FIDE_AI_MODEL=<tag>` measures another downloaded model, as the commit message replay also takes: on qwen3-coder, every task passes but the large-codebase question (it names the file providing `DartAnalyzer`, not the one declaring it, as MiMo does), rename ~6 s, feature ~17 s, Fix Build ~20 s; run the feature and Fix Build tasks 5 times or more before comparing models, as 3 runs once showed MiMo passing every one
  - the AI commit message reads a `CommitDigest` of the staged changes (files, documentation and declarations added and removed, declarations renamed, code moved unchanged, tests added and removed, then the code left changed), never the head of the diff, with the project's recent subjects as its style
    - code moved reads as moved, never as added: read as added, a State moved beside its widget made qwen3-coder write "Rectangle adjuster: Enable draggable corners…" for a refactor
    - code decides from the recent subjects whether the message starts with an area and a colon (most of them do, or there are none) or with a verb, as a project without areas has; told to start with an area, the model does whatever the examples show
    - tried and dropped: a word cap taken from the recent subjects, test code in the changes section (both slower, no better), an instruction that moved code is no feature (longer replies; the digest alone suffices)
    - re-measure it with `FIDE_AI_REPLAY=12 flutter test test/commit_message_replay_test.dart`, which replays recent commits on the local model; `FIDE_AI_REPLAY_REPO=../mural` replays another project's, and `FIDE_AI_REPLAY_STAGED='<message written by hand>'` adds its staged change: on qwen3-coder, 34% of FIDE's hand-written subject's words, its area named 3 times in 12 (most recent areas are longer than the 40 characters the test reads), ~2.4 s each; 36–40% of mural's, ~1.7 s each

# Workflow

- after making changes, always offer a one-line git commit message covering all pending changed files; don't commit unless asked
- when given a new rule or standing instruction, add it to this file, not only to private agent memory
